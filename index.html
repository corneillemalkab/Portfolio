TECHNICAL CASE STUDY & BIOGRAPHY

Inside Project AetherNet: The Engineering Story

A comprehensive architectural deep-dive documenting the design rationale, technical hurdles, and enterprise solutions implemented in Project AetherNet.

01

The Problem Context & Architecture Origin

Modern enterprise organizations migrating mission-critical workloads to Microsoft Azure frequently encounter severe operational bottlenecks when attempting to integrate with existing on-premises datacenters. Generic hub-and-spoke tutorials assume clean, cloud-native environments—ignoring the reality of legacy Active Directory dependencies, complex routing tables, and hybrid security mandates.

Project AetherNet was engineered to solve the four most critical hybrid cloud challenges: DNS forwarder loops, asymmetric traffic drops across next-gen firewalls, manual static route fragility during WAN brownouts, and accidental public IP exposure on cloud PaaS services.

02

BGP Dynamic Routing over Redundant IPsec VPN Tunnels

To eliminate the operational overhead and single-point-of-failure risks associated with static route tables, the architecture establishes a dynamic BGP peering session between an on-premises Windows Server 2022 Routing and Remote Access (RRAS) router (running as an enterprise gateway on Hyper-V under ASN 65010) and an Azure Virtual Network Gateway (VpnGw2AZ under ASN 65515).

  • Active-Active Dual Tunnels: Two independent IPsec IKEv2 tunnels provide automatic, hitless failover with convergence times under 2.8 seconds.
  • Automated Route Redistribution: On-premises VLAN subnets (10.0.10.0/24 and 10.0.20.0/24) and Azure Spoke address spaces (10.101.0.0/16 and 10.102.0.0/16) are automatically advertised without manual intervention.
03

Solving the Private Link DNS Split-Horizon Challenge

When Azure PaaS resources (such as Azure SQL and Blob Storage) are converted to Private Endpoints, their FQDNs resolve to canonical names (CNAMEs) like *.privatelink.database.windows.net. Without proper split-horizon DNS, on-premises clients query public DNS servers and receive unroutable public IPs or fail resolution entirely.

Instead of managing expensive, high-maintenance custom Linux/Windows VM forwarder clusters, Project AetherNet implements the native Azure Private DNS Resolver:

  • Inbound Endpoint (10.100.2.4): Windows Server 2022 Active Directory DNS servers forward all *.privatelink.* queries directly to this IP, achieving average query response times of 2.1 ms.
  • Outbound Endpoint & Rulesets: Azure workloads seamlessly query the on-premises domain (corp.aethernet.local) by forwarding requests back to on-prem domain controllers (10.0.10.10).
04

Zero-Trust Deep Packet Inspection & FinOps Governance

Project AetherNet enforces zero-trust micro-segmentation across both the network perimeter and internal lateral pathways:

  • Centralized Azure Firewall Premium: User-Defined Routes (UDRs) applied to all Spoke subnets force all outbound internet and cross-spoke traffic (0.0.0.0/0) through 10.100.1.4 for IDPS signature inspection, URL categorization, and TLS termination.
  • PaaS Isolation: All public network access is disabled on Azure SQL, Storage, and Key Vault. Connectivity is restricted strictly to Private Endpoints inside 10.102.1.0/24.
  • FinOps Drift Engine: Automated PowerShell scripts running in GitHub Actions CI/CD continuously audit unattached NICs, idle Public IPs, and overly permissive NSG rules—saving thousands in recurring cloud waste.
